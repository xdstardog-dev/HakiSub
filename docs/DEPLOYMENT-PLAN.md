## 用户提供的环境（待连接后核实）

阿里云广州轻量应用服务器，Ubuntu 24.04 LTS，2核、2GB内存、2GB Swap、40GB SSD；Docker Engine 29.9.1、Compose v5.6.0，用户 admin 可 sudo。目标目录仅为 `/srv/projects/hakisub`。服务器还有其他项目，资源预算须在只读检查后调整。

## 当前代码结论

- `server/roomGateway.mjs` 提供 `/api/rooms` WebSocket：服务端创建/加入、六位码、每房最多8人、连接绑定成员身份、成员快照、字幕/撤回广播、心跳与离房清理。新成员不接收历史字幕，最后一人离开销毁房间。
- 每人设备独立采集和VAD，`asrSession.ts` 给字幕绑定成员与会话标识。豆包经 `/api/asr?session=临时成员令牌` 使用独立上游连接，网关默认总共最多8路、每成员一路。VAD在浏览器Worker运行，服务器不做模型推理。
- 豆包结果先回到本人的浏览器，再通过房间连接广播统一字幕事件；不是服务器直接将供应商结果广播。身份由房间连接确定，但不验证文字必然来自真实ASR，当前仅适合受控可信测试。
- `npm run dev` 同时启动 Vite 5173 与网关8787；正式模式先构建，再 `npm start`，由单个 Node 进程同时提供 `dist/`、房间WebSocket和ASR网关，不需要运行 Vite。
- `captions.ts` 维持确认后3/6/10秒加2秒渐隐；字幕在页面内存，无历史落盘。新部署保持这些规则。
- 当前工作区有未提交的房间代码，包含未跟踪的新文件；部署须使用完整审查快照或经用户要求提交的版本，不能假设远端 Git 已包含这些改动。

## 部署前需要的本地适配（本轮尚未修改业务代码）

1. 监听地址改为可配置，保留本机默认127.0.0.1；容器中监听0.0.0.0，宿主机只发布127.0.0.1，避免容器回环地址导致端口映射不可达。
2. 测试部署禁用无成员令牌的旧ASR入口，仍保留本地开发兼容能力；为部署设置明确的ASR并发上限，先2后8。
3. 禁用共享测试端的密钥管理/测试接口，密钥只由服务器环境注入。仅校验localhost Host/Origin不是管理员权限，因为隧道测试者也使用localhost。
4. 添加明确文件白名单的镜像打包与`.dockerignore`，不发送本机`.env`、Git数据、SSH文件、独立Sites工作区或其他项目。固定Node基础镜像的具体版本/摘要并保留发布标识。
5. 新增部署配置测试，验证容器监听、无令牌ASR拒绝、设置接口关闭、并发限制；保留现有通信和音频模拟测试。

## 第一阶段推荐拓扑

```text
授权测试者电脑浏览器 http://localhost:本地端口
  → 绑定本机回环地址的 SSH 本地转发
  → 服务器 127.0.0.1:8787
  → Docker 映射至容器 8787（Node 在容器内监听 0.0.0.0）
  → 单个 HakiSub Node 进程提供网页与两条 WebSocket
  → 通过出站加密连接访问豆包
```

不新开公网80、443或8787，不新增数据库、Redis、Nginx、PM2或监控服务。访问授权依赖各测试者独立的SSH凭据；六位房间码不作为服务器访问认证。不共享admin私钥给其他测试者。若测试者缺少SSH权限，先提出独立、受限转发授权方案，再请求确认；不擅自新建用户或更改登录配置。

每台测试电脑的隧道必须连接同一台服务器。优先使用当前允许的localhost:8787；若本机现有服务占用该端口，保留旧服务，改用经配置明确允许的其他localhost端口。不能把浏览器连接留在旧本机网关。手机不在本方案的直接覆盖范围，后续另行安排私有HTTPS接入；HTTP公网IP不能替代麦克风安全上下文。

Docker仅将服务发布到宿主机回环地址；不修改Docker全局daemon、其他容器或共享代理配置。回环地址仍可被服务器本机有权限的进程访问，并非隔离服务器管理员。

## Compose及资源设计（规划值，待实机验证）

单服务、单实例、独立Compose项目名 `hakisub-test`。本地构建前端，将`dist/`及Linux运行时镜像所需白名单文件打包；服务器不运行Vite/TypeScript构建，Linux依赖在镜像内按锁文件安装，不能上传Windows node_modules。

| 项目 | 初始建议 |
| --- | --- |
| 启动 | `node server/index.mjs --production` |
| 端口 | `127.0.0.1:8787:8787`（实际须检查占用） |
| 容器内存上限 | 512MiB |
| 内存软预留 | 128MiB，非实测占用保证 |
| Node堆上限 | 256MiB，非进程总内存上限 |
| CPU | 0.75核，依据现有项目负载调整 |
| PID限制 | 64 |
| 自动重启 | `unless-stopped`，不由健康检查直接触发重启 |
| 运行权限 | 非root、只读根文件系统、必要的临时目录tmpfs |
| 容器权限 | 丢弃不需要的capability、no-new-privileges、不挂Docker socket |
| 日志 | stdout/stderr，json-file，每份10MB、最多3份 |
| 健康检查 | 只检查本地HTTP，不调用豆包；单独核对Key是否已配置 |
| 退出 | SIGTERM及约20秒退出宽限；升级会清空房间并中止当前识别 |

这些是限制与调优起点，不是“已测8人只占多少内存”的结论。Swap仅作为系统缓冲，不保证并发性能。须看实际剩余资源后再决定是否部署；不得挤占另外三个项目。

## 敏感配置、日志与回滚

- 豆包Key由用户在服务器本地交互输入，存放项目独立受限文件（例如`secrets/server.env`，目录0700、文件0600），运行时通过Compose `env_file`注入；仓库、Dockerfile、构建参数、镜像层、前端均不含Key。服务器环境变量优先于根目录`.env`，现有代码支持该路径。
- 环境变量并非加密保险箱；服务器root及Docker管理权限持有者仍可读取。禁止输出完整环境、无过滤`docker inspect`或展开敏感值的`docker compose config`。配置校验使用静默模式。
- 调试统计默认关闭；不记录音频、字幕、Key或含`session`查询参数的URL。不配置访问日志时也不应临时打开会暴露令牌的原始请求日志。
- 发布包有版本号/校验值；旧镜像及配置保留用于回滚。只操作本项目Compose，不做全局prune、删除目录、迁移数据库或停止其他项目。

## SSH建立与远程检查的确认点

已只读确认Windows存在 `C:\Windows\System32\OpenSSH\ssh.exe` 与 `ssh-keygen.exe`，尚未调用它们建立连接或创建密钥。

下一步先取得公网IP、现有SSH端口、是否已有适用密钥，以及用户对SSH连接准备/只读检查的明确确认。私钥与口令只在用户本机输入或由本机agent持有，绝不发到聊天。

若没有可用密钥：先展示使用独立文件名、带口令的Ed25519密钥生成步骤；服务器只追加公钥到admin的authorized_keys，须另获确认，不能覆盖已有授权。保留现有终端，先核验服务器主机密钥指纹，再在第二条连接验证密钥登录；不使用禁用主机校验的参数，不修改sshd配置，不擅自将密钥通过可能要求重启实例的云端操作绑定。

获准连接后的只读检查范围：系统版本、CPU架构、内存/Swap、磁盘余量、Docker/Compose版本、现有容器名称与资源使用、监听端口、目标目录是否存在及其权限。不读取其他项目配置、容器环境或任何密钥。目录创建、上传文件、启动容器、隧道转发或端口映射分别列出具体命令和影响后确认；安全组/防火墙变更另行确认，本方案通常无需新增网站入站端口。
